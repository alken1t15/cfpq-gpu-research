# CUDA-профиль после раннего выхода и проверка на других графах

После сокращения медианы luindex с 219,165 до 144,788 с проверяем, какие CUDA-вызовы и ядра остаются заметными. Отдельно проверяем, переносится ли выигрыш на xz и apache. Исходная библиотека и кандидат взяты из эксперимента [empty fill](../2026-11-23-empty-fill-alias/README.md). Хеши библиотек, бинарника и входов сверяются с предыдущими измерениями.

В WSL из корня репозитория:

```bash
python3 scripts/trace-gpu-empty-fill-luindex.py
python3 scripts/check-gpu-empty-fill-alias.py --graph xz
python3 scripts/check-gpu-empty-fill-alias.py --graph apache
```

Профилируем полный luindex/incremental в Nsight Systems, CUDA trace без CPU sampling и context-switch tracing. Проверяем 9 677 пар, затем экспортируем агрегаты CUDA API, ядер и передач памяти. Суммарные времена вызовов и устройств могут перекрываться. Время профилированного процесса используется для диагностики.

На xz и apache выполняются по одному прогреву на библиотеку и пять пар непрофилированных замеров с чередованием порядка. Во всех повторах общие бинарник CFRA и вход для каждой задачи. Контрольные количества — 358 834 и 92 806 768. Таймаут 900 секунд на запуск. Все этапы идут последовательно. Сырые результаты, включая бинарную трассу, локально в data/flpq-all.

Профиль завершён. Парные проверки xz и apache завершены.

## Результат профиля luindex

Ответ 9 677, AnalysisTime 143,917 с. Nsight Systems 2026.1.3, профиль и выгрузка таблиц завершились с кодом 0. Сумма длительностей CUDA API — 131,961 с. Из неё 51,351 с и 1 913 544 вызова приходятся на cudaStreamSynchronize, 42,805 с и 912 689 вызовов — на cudaMemcpyAsync, 15,584 с и 1 414 838 вызовов — на cudaLaunchKernel. API-вызовы могут включать ожидание другой работы.

Объединение интервалов KERNEL, MEMCPY и MEMSET даёт 25,697 с активности в пределах 143,722 с между первой и последней GPU-операциями. Интервалы объединены по start/end в SQLite, чтобы учесть пересечения. Сумма длительностей ядер — 23,179 с, из которых 15,033 с относятся к одному ядру count_nz с 96 039 запусками. Среди копирований с устройства на хост 613 604 передачи по 4 байта и 192 078 по 36 байт.

Подтвердились большие накладные расходы на управление мелкими операциями. Кандидат на следующий изолированный эксперимент — сократить число отдельных чтений метаданных и синхронизаций. Для выбора правки нужно привязать передачи к конкретным местам в count/fill. Агрегаты профиля сами по себе не показывают, какую долю времени устраняет правка.

Локальные файлы: gpu-empty-fill-profile/luindex-stats.csv, luindex.sqlite, luindex.nsys-rep. Ход контрольной серии: gpu-empty-fill-cross-check.log.

## Атрибуция мелких чтений

```bash
python3 scripts/attribute-luindex-d2h.py data/flpq-all/gpu-empty-fill-profile/luindex.sqlite --out data/flpq-all/gpu-empty-fill-profile/d2h-attribution.json
```

В трассе один процесс и нет стеков CUDA API. Атрибуция основана на порядке correlationId, повторяющихся границах count/fill и чтении исходников. Зафиксированы 96 039 начальных ядер count_nz и столько же завершающих cudaDeviceSynchronize. В каждой группе ровно два чтения по 36 байт. Это согласуется с преобразованием двух массивов девяти корзин в host_vector для exec_block_row.

Перед двумя пакетными чтениями наблюдаются 126 492 чтения по 4 байта, что согласуется с обращениями exec_pwarp_row к device_vector. После пакетных чтений и до cudaDeviceSynchronize — 96 039 чтений по 4 байта, по одному на произведение, что согласуется с чтением размера глобальной корзины в exec_global_row. Первое чтение после cudaDeviceSynchronize есть во всех 96 039 группах. По коду ему соответствует чтение row_idx.back() для раннего выхода. В окнах между маркерами fill_nz и следующим count_nz обнаружены 160 815 чтений по 4 байта. В эти окна могут попадать последующие операции, поэтому это верхняя граница числа чтений в fill_nz, а не точная атрибуция.

Следующий кандидат — перенести уже выполняемые две копии массивов корзин перед exec_pwarp_row и использовать эти данные на хосте в трёх путях запуска count_nz. По трассе до 222 531 отдельных чтений могут относиться к этим участкам. Реальное число исключённых передач и влияние на время нужно проверить на отдельной CUDA-сборке. Результат ускорения пока не измерен.
