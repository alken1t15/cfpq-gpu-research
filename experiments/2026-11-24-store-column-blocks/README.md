# Умножение блоков столбцов для правил store в CFRA

Гипотеза: для семейства `Al_store_i → Al store_i` несколько произведений с общим левым операндом можно заменить одним произведением с горизонтально объединёнными правыми матрицами. Блок i начинается со столбца i*n. После умножения результат режется на исходные столбцовые блоки и объединяется с временной матрицей каждого правила. Фазы M×Δ и Δ×M группируются отдельно. Максимальный размер пакета 16, с проверкой допустимой размерности. Остальные правила обрабатываются штатно.

CUDA-проверка на малых матрицах, включая пустые блоки и накопление, прошла 60 конфигураций и 240 сравнений точных множеств пар. Попытка извлечения подматрицы при полностью пустом операнде вернула статус 1. В пробной реализации целиком пустой результат пропускается. Сбой API отдельно не исправлялся.

На luindex сравниваем одну пару полных процессов на одинаковой проверенной fill-host-bins библиотеке. В тестовом исполняемом файле пересобран только incremental_algo. Подготовка блоков и извлечение результатов входят во время. Записываем ответ, число вызовов MxM кандидата и общий максимум использования VRAM по секундным отсчётам nvidia-smi. Это оценка по устройству, краткие пики возможны между отсчётами. Одна пара служит для первичной оценки.

```bash
python3 scripts/check-store-column-blocks.py --out data/flpq-all/store-column-blocks.json
python3 scripts/trial-store-column-blocks.py --out data/flpq-all/store-column-blocks-luindex-retry
```

Первый пробный запуск сборки остановился из-за отсутствующего include для CB_CHECK. После добавления common.hpp запущена новая попытка с отдельным каталогом. Повтор завершился успешно.

## Идеи из литературы

- [Муравьёв, 2024, §3, оптимизация 4](https://arxiv.org/html/2401.11029v1). Для индексированного нетерминала автор хранит горизонтальную и вертикальную блочные матрицы целого семейства. Это сокращает число произведений до числа шаблонов правил. Наш прототип собирает и разбирает блоки при каждом пакете. Следующая гипотеза — повторно использовать упаковку правого операнда в фазе Δ×M. Перед кешированием надо подтвердить неизменность матриц store_i: исключить правила, которые их дополняют, либо привязать кеш к версиям матриц и точному составу пакета.
- [Nagasaka и др., Batched SpMM, §IV-C](https://arxiv.org/html/1903.11409). Авторы обрабатывают много небольших операций одним запуском ядра и подбирают разбиение по размерам. У них разреженная матрица умножается на плотную. Для наших булевых разреженных матриц это мотивирует проверить размер пакета, а не переносить ядро или опубликованные ускорения.
- [Du и др., OpSparse, §4.4–4.6 и §5](https://arxiv.org/html/2206.07244). В SpGEMM сокращают объём временных метаданных и совмещают выделение памяти с вычислением. Для cuBool возможен отдельный опыт с повторным использованием буферов. Проверять число выделений, пиковую VRAM и полное время. Времена из статьи относятся к другой нагрузке и GPU.

Первый эксперимент после прямого сравнения разборов — измерить, сколько пакетов в фазе Δ×M имеют одинаковый упорядоченный набор правых матриц и сколько времени занимает их упаковка. Если повторов достаточно, проверить кеш на точных множествах пар малых матриц, затем провести пять чередующихся пар на luindex с одинаковым способом разбора. На эталоне ожидается 9 677 пар; отдельно фиксируются попадания в кеш, память и полное время. Новых GPU-прогонов при подготовке обзора не запускали.

### Транзитивные правила и неизменные операнды

POCR хранит деревья достижимости для транзитивных отношений и использует их при выборе порядка вывода. PEARL строит граф распространения и передаёт по нему сразу множества достижимых вершин. Для правила X → X A достаточно распространять X по рёбрам A, сохраняющим достижимость, без повторного вывода через транзитивно избыточные рёбра. Это отдельный подход, отличный от упаковки нескольких произведений в одну матрицу. [POCR, §4](https://yuleisui.github.io/publications/oopsla22.pdf) · [PEARL, §III–IV](https://enochii.github.io/publications/ase23-pearl.pdf)

Грамматика luindex содержит PTh → assign PTh и FTh → FTh assign_r. Это кандидаты для отдельной диагностики распространения по цепочкам assign. Семейство Al_store_i → Al store_i устроено иначе: выход отличается от обоих операндов. Переносить приём PEARL непосредственно на это семейство оснований нет.

В грамматике luindex store_i используется справа и отсутствует слева во всех правилах. CFRA загружает рёбра с этими метками из входного графа. Следовательно, в фазе Δ×M для выбранной грамматики можно повторно использовать готовую упаковку, если совпадает упорядоченный состав пакета. В фазе M×Δ входные приращения меняются. Для общего случая кандидат должен проверять условие неизменности по раскрытой грамматике. Сначала измеряем повторяемость пакетов, затем решаем, оправдан ли кеш.

### Ночная серия на графах из отчёта

`bash scripts/run-gpu-report-overnight.sh data/flpq-all/gpu-report-overnight-2026-11-25`

Сначала измеряем сборку fill-host-bins на семи исходных парах графа и грамматики из benchmark-cases.csv. Для каждого из режимов base, incremental и lazy предусмотрены проверка, прогрев и пять измерений. Затем на тех же семи входах и дополнительно на lusearch сравниваем incremental с кешем пакетов и без него. Для каждого графа предусмотрены два прогрева и 15 чередующихся пар, лимит 900 секунд на запуск. Для графов без подходящих правил допускается ноль попаданий в кеш. GPU-задачи выполняются последовательно. Профилировщик отключён в обеих сериях.

Время измеряется по полному запуску процесса. Хеши графов и грамматик из отчёта сверяются с сохранёнными манифестами. По каждому запуску фиксируются ответ и длительность, по каждому этапу сохраняется код завершения. Очередь запущена, результатов на момент записи пока нет.

Ночной прогон закончился в 07:36 МСК. Из 147 запланированных запусков 145 вернули эталон, 2 превысили лимит 900 с: прогрев luindex/base и пятый замер unigraph_3/base. В первом случае пять измеряемых запусков прошли; во втором есть четыре успешных замера. Сравнение кеша завершилось на 7 из 8 графов; luindex остановился на прогреве с кешем. У всех трёх таймаутов stdout и stderr пусты, причина не установлена.

На lusearch все 15 пар вернули 9 242 пары при 62 187 MxM, медианы 71,494 → 69,394 с, кеш быстрее в 13/15 пар. В каждом запуске с кешем 858 попаданий. На остальных шести графах завершённых серий попаданий не было, поэтому их различия времени не следует приписывать повторному использованию упаковки.
