# Умножение блоков столбцов для правил store в CFRA

Гипотеза: для семейства `Al_store_i → Al store_i` несколько произведений с общим левым операндом можно заменить одним произведением с горизонтально объединёнными правыми матрицами. Блок i начинается со столбца i*n. После умножения результат режется на исходные столбцовые блоки и объединяется с временной матрицей каждого правила. Фазы M×Δ и Δ×M группируются отдельно. Максимальный размер пакета 16, с проверкой допустимой размерности. Остальные правила обрабатываются штатно.

CUDA-проверка на малых матрицах, включая пустые блоки и накопление, прошла 60 конфигураций и 240 сравнений точных множеств пар. Попытка извлечения подматрицы при полностью пустом операнде вернула статус 1. В пробной реализации целиком пустой результат пропускается. Сбой API отдельно не исправлялся.

На luindex сравниваем одну пару полных процессов на одинаковой проверенной fill-host-bins библиотеке. В тестовом исполняемом файле пересобран только incremental_algo. Подготовка блоков и извлечение результатов входят во время. Записываем ответ, число вызовов MxM кандидата и общий максимум использования VRAM по секундным отсчётам nvidia-smi. Это оценка по устройству, краткие пики возможны между отсчётами. Одна пара служит для первичной оценки.

```bash
python3 scripts/check-store-column-blocks.py --out data/flpq-all/store-column-blocks.json
python3 scripts/trial-store-column-blocks.py --out data/flpq-all/store-column-blocks-luindex-retry
```

Первый пробный запуск сборки остановился из-за отсутствующего include для CB_CHECK. После добавления common.hpp запущена новая попытка с отдельным каталогом. Повтор завершился успешно.

## Результат

Обе версии вернули 9677 пар (exit 0). Полное время исходного и блочного вариантов: 310,745 и 304,551 с (−2,0%). AnalysisTime: 130,145 и 124,076 с. Пиковая видеопамять по секундным отсчётам на устройстве: 819 и 800 МиБ. Кандидат выполнил 79 639 MxM против 96 039 в отдельной предшествующей диагностике исходного алгоритма (−17,1%). В этой паре счётчик исходной версии не снимался. Одна последовательная пара не подтверждает устойчивого ускорения; значительная часть полного времени была вне AnalysisTime. Сырые результаты: data/flpq-all/store-column-blocks-luindex-retry.

## Разбор затрат по фазам

Команда `python3 scripts/trial-store-column-blocks.py --phase-timing --out data/flpq-all/store-block-phase-timing` завершилась с 9677 парами и 79 639 MxM. На 1120 многоблочных произведениях сумма времени упаковки — 5,132 с, вызова MxM с чтением размера — 1,781 с, разрезания и объединения — 5,593 с. Это интервалы на хосте, включая ожидание CUDA внутри API. Одноблочные обходные пути, освобождение части временных объектов и оставшаяся работа CFRA в этих суммах не учтены. Полное время диагностического запуска — 139,760 с.

В изолированном варианте `--single-unpack` извлекаем все пары произведения одним вызовом и по частному и остатку номера столбца восстанавливаем нужную матрицу. Пустые части пропускаем. Проверка на малых матрицах прошла 60 конфигураций и 240 сравнений множеств. На luindex запущены прогрев обеих версий и пять чередующихся пар обычного алгоритма и нового блочного варианта; исходная библиотека для обеих версий одинакова, таймеры фаз выключены. Отчёт data/flpq-all/store-single-unpack-pairs, журнал store-single-unpack-pairs.log. Итог ещё ожидается.

## Повтор серии с однопроходным разбором

Первая серия прервалась на второй паре без итогового файла. Повтор в data/flpq-all/store-single-unpack-pairs-restart завершён. Все десять измеряемых запусков вернули 9677 пар. Медиана полного времени обычного алгоритма — 113,659 с, блочного с однопроходным разбором — 95,591 с (−15,9%). Кандидат быстрее в трёх из пяти пар. Диапазоны 103,970–137,550 с и 92,130–153,297 с перекрываются. Серия измеряет эффект блочного варианта целиком. Вклад однопроходного разбора отдельно пока не измерен.
