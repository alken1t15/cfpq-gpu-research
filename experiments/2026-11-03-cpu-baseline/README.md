# CPU baseline: исправленный incremental на luindex

Дата: 2026-11-03. Цель: получить воспроизводимую точку отсчёта для последующих экспериментов. Это не сравнение CPU с GPU и не доказательство ускорения относительно исходного CFRA с неправильным ответом.

## Код и вход

База CFRA 3bc9794a509ca2f40c82b04e6c31e21ef9d1dbf1 плюс правка раскрытия шаблонов и предупреждение. SHA256 бинарника, графа, грамматики и патча — manifest.json. Патч отслеживаемых файлов — tracked-changes.patch. cuBool 1d4e760bc0d76906b81c70c505d6b29b4d9d3f11.
Вход: FLPQ_Data v6 luindex, 18532 вершины, 34750 рёбер после обратных, явно адаптированные метки; java_points_to.cnf без изменений. Происхождение, SHA256 архива и mapping в ../2026-11-03-java/manifest.json.

## Среда

Ubuntu22.04 WSL2, GCC13.4, CMake3.22.1, Release, CPU sequential fallback cuBool, CPU i7-11370H. Полный снимок окружения: ../2026-11-03-wsl-cpu/environment.log. Драйвер и GPU указаны там для контекста, но GPU здесь не используется. Файлы хранятся на /mnt/d; перенос на Linux FS может повлиять на полное время процесса.

## Методика

```powershell
wsl -d Ubuntu -- python3 /mnt/d/semen_task_avtomat/scripts/benchmark-cpu.py
```

Один прогревочный процесс, затем пять измеряемых; последовательные запуски, без одновременного профилирования/других тестов со стороны агента. Каждый запуск новый процесс с --algo incremental --cpu и таймаутом 120с. Прогрев подготавливает системные кэши, а не сохраняет состояние backend между процессами. Состояние питания/нагрев и посторонняя пользовательская нагрузка не контролировались.

На каждом повторе обязательны код 0, пустой stderr и 9677 пар. Вывод каждого процесса сохраняется. wall_seconds — Python perf_counter вокруг запуска/завершения процесса: включает загрузку, расширение грамматики, backend, анализ и завершение. analysis_seconds — напечатанный AnalysisTime: внутренний таймер алгоритма после загрузки графа, расширения грамматики и cuBool_Initialize; включает построение матриц, не включает полное завершение процесса. Не смешивать две области измерения.

Summary строится только по пяти измеряемым повторам: медиана, min/max, среднее и выборочное стандартное отклонение. Никакого выбора «самого удачного» повтора.

## Результаты и ограничения

Сырые данные — raw.json, сводка после завершения — summary.json. Эталон проверяет количество, не сами множества пар. Одна грамматика, один граф и один backend не обосновывают общие выводы о производительности. Для сравнения будущей оптимизации повторять сопоставимую методику, сохранять правильность ответа и фиксировать новый бинарник/патч. Исходную версию с 7472 парами нельзя использовать как корректный performance baseline.
