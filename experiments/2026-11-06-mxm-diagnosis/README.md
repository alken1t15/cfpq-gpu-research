# Диагностика GPU MxM: редукция счётчиков строк

Дата:2026-11-06. База исследования:4c74a2d25aa31eef2a9bdfcca0c49c2003a8939a, cuBool fork37ccfd8 с PR19. RTX3060Laptop8.6, CUDA12.4, WSL. Ветка research/gpu-mxm-diagnosis. Production-код не менялся; trial подставлен только через отдельную библиотеку.

## Воспроизведение

Матрицы3×3: A={(1,0),(1,1),(2,0),(2,2)}, B={(0,0),(1,1),(2,1),(2,2)}. Ожидаемые количества уникальных столбцов по строкам произведения:[0,2,3]. Прямой вызов count_nz_pwarp_row<unsigned,4,256,32> выдаёт[0,2,1] пять раз подряд. Таким образом ошибка существует до fill_nz и вне API CFRA/cuBool. Пять повторов одного входа не являются статистическим исследованием.

Первый standalone compile не прошёл: header util.h использует thrust::host_vector без собственного include. В пробу добавлен явный include thrust/host_vector.h; production не менялся. После этого компиляция успешна. Ошибка сборки самой библиотеки не заявляется.

## Гипотеза и вмешательства

count_nz_pwarp_row считает локальные nz в четырёх потоках на строку. После неодинаковых циклов вызывает __activemask(), затем shuffle-суммирование. Такая маска описывает потоки, исполняющие инструкцию в этот момент; она не задаёт гарантированный состав группы для редукции. Документация NVIDIA описывает аналогичный риск: https://developer.nvidia.com/blog/using-cuda-warp-level-primitives/.

В отдельных копиях header проверены два вмешательства, по одному за сборку: (1)__syncwarp перед получением mask; (2)получение mask до циклов. Обе версии дали[0,2,3] во всех5 повторах. Это локализует дефект к редукции/составу участников; дальнейшее исправление должно задавать гарантированный состав группы, а не полагаться на случайную синхронность.

## Trial cuBool

Скомпилирован только cuda_matrix_multiply.cu.o с experimental early_mask header, остальные объекты взяты из GPU-only build/gpu-cubool-pr19. Baseline SHA256 до/после совпадает. Новая library build/mxm-diagnosis/libcubool.so. Команды и хеши:trial-commands.json,trial-manifest.json. Патч early-mask.patch — кандидат для исследования, пока не интегрирован в исходники.

Малые прямые пробы:baseline23/24,trial24/24. Расширенные полные множества:baseline592/864,trial622/864. У trial все distinct-output и все accumulate=true случаи прошли; оставшиеся242 несовпадения только при alias входа и результата, accumulate=false. Они отделены от найденной редукции: CudaMatrix::multiply очищает result перед чтением входов. Контракт поддержки alias ещё требует уточнения, поэтому это не объявлено новым установленным нарушением API.

Внешняя проверка:atom,bzip,pizza,gzip ×base/incremental/lazy —12/12 эталонных количеств. CFRA CLI проверяет только число пар, а не полное множество. luindex/incremental ограничен30с; результат см.catalog-trial.json. gson и остальные luindex-конфигурации в этой ограниченной серии не запускались. Общая GPU-корректность и ускорение не заявляются.
