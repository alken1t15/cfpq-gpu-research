# Расширенная CPU-проверка fast path по каталогу

Дата: 2026-11-03. Цель — проверить корректность опытной CPU-библиотеки на разных входах и всех трёх CFPQ-алгоритмах. Серия завершена, код скрипта 1 из-за двух таймаутов.

```powershell
wsl -d Ubuntu -- python3 /mnt/d/semen_task_avtomat/scripts/check-cpu-trial-catalog.py
```

Запланированы atom, bzip, pizza, gzip, luindex, gson: RDF, C alias и Java points-to. Для каждого графа выбрана одна каноническая грамматика с опубликованным эталоном, запускаются base/incremental/lazy на baseline и fast_path. Один процесс на конфигурацию, таймаут 120 секунд; это проверка корректности, не performance benchmark. В stdout сохранены времена, но они не используются для выводов о скорости, в том числе потому что параллельно устанавливалась/собиралась CUDA-среда.

Версии библиотек и бинарника — manifest.json по завершении, входные URL, SHA256 архивов/графов/грамматик, размеры и полная таблица меток — inputs.json. Таблица эталонов reachable_pairs.csv сохранена. Архивы из https://cfpq-data.storage.yandexcloud.net/6.0.0/graph/. Данные исключены из Git. Датасет FLPQ_Data — CC-BY4.0, источник https://github.com/FormalLanguageConstrainedPathQuerying/FLPQ_Data.

Добавляются обратные рёбра. Для Java применяется согласованный mapping load_k → load_i_k, store_k → store_i_k и load_r_i_k/store_r_i_k для обратных. Грамматики не меняются. Размерности и представленность всех вершин проверяются; вход с потерей изолированных вершин не принимается молча.

Сравнение — только количество пар CFRA CLI с опубликованным эталоном. Полные множества ответов CFPQ не извлекаются. Ранее прямые тесты матричного примитива сравнили полные множества: по 864 проверки на двух библиотеках; они не заменяют проверку CFPQ целиком.

База CFRA 3bc9794a509ca2f40c82b04e6c31e21ef9d1dbf1 плюс текущая правка парсера/диагностики, cuBool1d4e760bc0d76906b81c70c505d6b29b4d9d3f11. Baseline и trial выбираются LD_LIBRARY_PATH, исходники библиотеки не меняются. Ubuntu22.04WSL2, GCC13.4Release. Основной CPU-бинарник прежний.

Результаты сохраняются после каждого процесса в results.json; таймауты отражаются отдельным статусом, не нулевым временем. Ошибка/таймаут не считается успешной проверкой. Итоговая статистика добавляется после завершения.


## Итог

36 конфигураций: **34 совпали**, **2 таймаута**, неправильных завершённых ответов нет. Для atom/bzip/pizza/gzip/luindex все 30 проверок прошли. На gson baseline и fast_path с base не завершились за 120с; incremental и lazy дали эталон 56325 на обеих библиотеках (4/4). Таймауты не доказывают ни правильность, ни ошибочность ответа этих двух конфигураций. Это расширяет свидетельства корректности CPU fast path, но не расширяет измеренное утверждение 1.606× за пределы прежнего incremental/luindex benchmark.
