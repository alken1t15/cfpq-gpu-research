# CUDA trace GPU MxM и luindex

Дата: 2026-11-06. Статус: выполнено. Ветка research/gpu-cuda-trace, база 6ec4ccb. Production-код не изменён.

## Вопрос

Объясняется ли наблюдавшаяся высокая host CPU-доля libcuda частыми API-вызовами вокруг коротких GPU-операций? Предыдущий host-профиль не измерял длительности ядер; здесь они получены CUDA trace. Причина прежнего timeout отдельно не установлена.

## Окружение и происхождение

WSL2 Ubuntu, RTX 3060 Laptop, CUDA 12.4, Windows driver 621.01; исходники и бинарники прежней полной CUDA-only сборки. SHA256 приложений и библиотеки записаны в small/luindex-manifest.json и совпадают с интеграционным протоколом row-mask. Sequential fallback OFF. Изменений маски, alias или tile в этой сессии нет.

Установлен nsight-systems-2026.1.3 версии 2026.1.3.425-261338342291v0 из подключённого NVIDIA WSL APT repo: 422 MB, 15 новых пакетов, 0 обновлений, без рекомендованных пакетов. Linux display driver не устанавливался. install.log сохраняет фактический вывод APT; его необычную оценку дополнительного места не используем как измерение установленного размера. CLI сообщает работоспособное CPU environment; CUDA trace фактически проверен отдельно. Compute Sanitizer по-прежнему не проверялся повторно.

Вход luindex и грамматика прежние: FLPQ_Data v6, 18532 вершины, 34750 рёбер, адаптация Java-меток; SHA256 и mapping в ../2026-11-03-trial-catalog/inputs.json и ../2026-11-06-gpu-repeatability/manifest.json. Малый тест содержит матрицы 3×3 и пять ожидаемых пар.

Точные profile/stats команды в manifest. trace=cuda, CPU sample и context switches отключены. Малый тест запускается до завершения; luindex — первые 30 секунд с kill=sigterm. Прогрева и измеряемых повторов здесь нет: это диагностические профили с накладными расходами, а не baseline. Init и выделение памяти входят в trace. Внешний timeout runner 240 с; фактически не сработал. После profile выполняются cuda_api_sum, cuda_gpu_kern_sum и cuda_gpu_mem_time_sum в CSV; суммирование интервалов — отдельный скрипт.

Бинарные .nsys-rep и SQLite сохранены только локально в build/gpu-cuda-trace (luindex около 74/167 MB), SHA256 отчётов — manifest. В Git входят только скрипты, текстовые логи/CSV/JSON. Локальная справка CLI — profile-help.txt. [NVIDIA User Guide](https://docs.nvidia.com/nsight-systems/UserGuide/) описывает duration/kill и границы профилирования; параметры сверены с установленной версией.

## Корректность и статусы

Small: MultiplyDivergentSmallRows прошёл, profile exit0, stats exit0, CUDA API и 25 GPU-ядер присутствуют. Полный набор из пяти ожидаемых пар проверен самим C++-тестом. Это фактическая проверка CUDA trace в данном WSL/WDDM, а не предположение на основании документации.

Luindex: profile exit143 — ожидаемое завершение SIGTERM после окна 30с, stats exit0, stderr пуст. Полного ответа CFPQ нет; этот запуск нельзя считать успешной проверкой количества 9677 или новым timeout вычисления. При прежней непрофилированной серии один процесс дал9677, другой достиг300с без ответа; результаты не подменяются профилем.

## Наблюдения

В luindex записано 2 050 528 CUDA Runtime API-вызовов. Их объединённое время 26.253 с внутри span 28.860 с. GPU: 383750 ядер, сумма 3.543 с; объединение интервалов ядер 3.542 с. С учётом memcpy/memset объединение GPU-активности 4.161 с внутри span от первой до последней GPU-операции 28.689 с (около14.5%). Это не occupancy и не аппаратный счётчик utilization; промежутки без записанной активности не обязательно полностью устранимы.

## Гипотеза следующего эксперимента

Данные подтверждают большое число коротких GPU-операций и частых host/device взаимодействий в этом окне. Исходники count_nz.h и fill_nz.h читают bin_size/bin_offset через device_vector operator[] в условиях и параметрах запусков. Такие чтения — кандидат для объединения в одну host-копию метаданных по фазе. Также count_nz_functor каждый раз создаёт девять streams; 15750 cudaDeviceSynchronize и141750 stream create согласуются с этой структурой. Это сопоставление кода и trace, не точная атрибуция каждого memcpy к строке исходника.

Следующий шаг: отдельный trial только для пакетного чтения bin metadata, сохранив порядок готовности данных, explicit row mask и прочие алгоритмы. Сначала матричная корректность и внешний каталог; затем проверить снижение числа 4-байтовых копирований и сравнить непрофилированные повторы на одинаковой задаче. Stream reuse, alias и tile не смешивать с этим экспериментом. Ускорение и причина timeout текущим профилем не доказаны.

Уточнение размеров: copy_kind=2 содержит 232440 передач по4байта, 31500 по36байт и2949 по8байт; сумма266889 совпадает с DtoH-счётчиком штатного отчёта. Основная часть DtoH — скалярные передачи. Важно: count_nz::exec_block_row уже принимает thrust::host_vector по значению, поэтому часть пакетных копий существует сейчас. Кандидат должен вынести общую host-копию после готовности bin metadata и переиспользовать её между ветвями, а не добавлять ещё одну копию поверх старых. Точная атрибуция232440операций к конкретным строкам ещё требует отдельного измерения/контролируемого trial.
