Дата: 2026-11-03. Статус: выполнено успешно; ответ 9677, код 0.
Цель: выяснить, где тратится CPU-время корректной реализации. Это не профиль GPU и не тест ускорения.

## Воспроизведение

```powershell
wsl -d Ubuntu -- bash /mnt/d/semen_task_avtomat/scripts/profile-cpu.sh
```

Скрипт запускает `perf record -e cpu-clock:u -F 199 --call-graph dwarf,8192` для --algo incremental --cpu. Записаны 2642 samples, lost samples=0, файл 21.590 MB. perf.data хранится локально, исключён из Git; команда воспроизводит запись. Текстовые отчёты сохраняются рядом.

- query.stdout — stdout CFRA, включая AnalysisTime 13.4931 и #SEdges 9677.
- record.stderr — сообщения записи perf; stderr профилировщика не смешивается с обычным baseline.
- self-report.txt — собственное время функций со стеками.
- children-report.txt — включающее время со стеками.
- dso-report.txt — распределение собственных samples по библиотекам.
- top-self.json — компактная выписка собственных процентов.

## Наблюдения

Проценты — доли sampled user CPU time, не wall time и не точные длительности функций. Self и children не складывать: включающие доли родителей перекрываются.

| Место | Собственная доля |
|---|---:|
| cuBool sq_spgemm | 44.10% |
| cuBool sq_ewiseadd | 41.26% |
| vector<unsigned int>::_M_fill_insert в cuBool | 5.53% |
| cuBool sq_ewisemultinverted | 3.22% |
| memset в libc | 1.55% |

Суммарная доля libcubool.so по DSO: 95.72%. Включающая доля cuBool_MxM: 88.38%. Стек sq_ewiseadd распределён в основном через SqMatrix::multiply (37.66 процентных пункта собственного времени), отдельно через SqMatrix::eWiseAdd (3.60). В отчёте также видны выделение/инициализация векторов внутри этих операций.

Проверка кода: cuBool/cubool/sources/sequential/sq_matrix.cpp, SqMatrix::multiply, строки 150–169: sq_spgemm вычисляет отдельный CsrData, а при accumulate всегда вызывает sq_ewiseadd с накопленным результатом. sq_ewiseadd проходит все nrows при подсчёте и заполнении результата, даже для разреженных матриц. sq_spgemm также проходит строки и инициализирует маску размера ncols. Это структура просмотренного CPU-кода, а не измеренное распределение времени по строкам.

## Гипотезы для следующих экспериментов

1. Часть accumulated MxM может получать пустое произведение или пустую целевую матрицу; тогда общее объединение может быть избыточно. Сначала измерить количество таких случаев и размеры, затем проверить безопасный fast path. Сейчас частота неизвестна и выигрыш не доказан.
2. Много малых матриц одного большого размера могут создавать заметные затраты на обход пустых строк и инициализацию. Профиль и код согласуются с этим объяснением, но для проверки нужны счётчики размеров/nnz/числа операций или микробенчмарк; причинность ещё не установлена.
3. Локальный рефакторинг строковых map в управляющем алгоритме пока менее приоритетен: выборка показывает доминирование матричного backend. Это приоритет на данном входе, не общее утверждение.

## Ограничения

Один профиль одного входа и одного алгоритма; частота 199 Hz, возможны ошибки выборки и размотки оптимизированных стеков. Бинарник Release без дополнительной отладочной сборки; функции видны, точная построчная атрибуция не делалась. Потерянных samples perf не сообщил, но это не доказательство идеальной атрибуции. Анализ только user CPU: ядро, ожидания и GPU здесь не представлены. Профилированное AnalysisTime не использовать вместо baseline.

Следующий шаг — счётчики операций/пустых результатов в отдельной экспериментальной версии, без смешивания её времени с baseline. Параллельно по плану нужна подготовка CUDA toolchain и отдельный GPU-профиль, чтобы не переносить выводы CPU backend на GPU.
