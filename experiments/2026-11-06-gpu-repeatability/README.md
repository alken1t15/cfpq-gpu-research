# Предварительная повторяемость GPU incremental/luindex

Дата: 2026-11-06. База: 6ee1923, ветка research/gpu-luindex-repeatability. Алгоритм и библиотека не изменены.

## Вопрос и методика

Повторяется ли эталонный ответ 9677 и время на интегрированной CUDA-only сборке? Один отдельный процесс прогрева, затем два измеряемых процесса последовательно, лимит каждого 300 секунд. Два измерения выбраны для предварительной проверки из-за стоимости порядка трёх минут на запуск; этого недостаточно для устойчивого performance baseline. Прогрев относится к системным кэшам, каждый процесс создаёт собственный CUDA context.

Основная метрика — perf_counter вокруг subprocess.run до завершения процесса, включая чтение входов, раскрытие грамматики, CUDA initialization, вычисление, вывод и finalize. Это завершённый запрос, а не время запуска асинхронных ядер. Отдельные cudaDeviceSynchronize в код алгоритма не добавлялись. CLI AnalysisTime сохраняется только как вспомогательная метрика: t0 внутри run_cflr_incremental до MatrixStore, t1 до финального чтения start_nvals/total_nvals и деструкторов. CudaMatrix::getNvals возвращает mMatrixImpl.m_vals на CPU и само по себе НЕ является синхронизацией GPU. Поэтому AnalysisTime нельзя трактовать как точную сумму длительностей CUDA-ядер. count_nz.h содержит явный cudaDeviceSynchronize; это также не заменяет полного аудита границ таймера.

## Происхождение и воспроизведение

```bash
python3 /mnt/d/semen_task_avtomat/scripts/repeat-gpu-luindex.py
```

Runner отказывается перезаписывать raw.json. Он проверяет SHA256 cfra/libcubool.so против успешной интеграции row-mask, сохраняет SHA256 графа и грамматики, linkage, lscpu, uname и nvidia-smi. LD_LIBRARY_PATH явно выбирает интегрированную cuBool; sequential fallback OFF. Сборки и входы не меняются. Входы FLPQ_Data v6 luindex, адаптация меток и эталон — ../2026-11-03-trial-catalog/inputs.json. Размеры/раскрытая грамматика присутствуют в каждом stdout. Сравнивается количество пар, не множество ответов CFPQ.

Измерения выполняются без профилировщика и без параллельных экспериментов агента. Частоты/питание/температура не фиксируются принудительно; это ноутбук под WSL2, внешняя нагрузка не контролируется полностью. Предыдущую CPU-медиану из другого этапа не используем для заявления GPU/CPU speedup.

## Выбор профилировщика

Проверка command -v: nsys и ncu отсутствуют; perf доступен. Никакие пакеты в ходе измерений не устанавливались. perf показывает host CPU samples, а не GPU kernel durations; это возможный дополнительный инструмент, не замена CUDA trace.

По [руководству CUDA/WSL NVIDIA](https://docs.nvidia.com/cuda/wsl-user-guide/) Nsight Systems CLI и CUPTI trace поддерживаются в WSL; фактическую работоспособность здесь ещё надо проверить. Следующий инструмент для временной шкалы — Nsight Systems с CUDA trace: [официальное руководство](https://docs.nvidia.com/nsight-systems/UserGuide/). Отказ Compute Sanitizer на этой машине не доказывает отказ Nsight Systems. Установка и пробный trace остаются отдельным этапом после измерений. Аппаратные performance counters пока не требуются.

| Прогрев | exit0 | 224.855731 | 223.566 | 9677 |
| Измеряемый 1 | timeout 300 с | 300.371491 | нет | нет |
| Измеряемый 2 | не запускался после timeout | — | — | — |

Сырые результаты: raw.json. Медиана и стандартное отклонение не рассчитываются: нет завершённых измеряемых запусков. Таймаут не является нулём, неверным ответом, доказательством deadlock или доказательством конкретного узкого места. SHA256 входов/бинарников сохранены в manifest.json; linkage подтверждает нужную cuBool. Более ранний успешный AnalysisTime170.584 из интеграционного протокола не аннулируется, но не является устойчивым временем для всех повторов.

На этой машине повторяемость завершения luindex в лимите 300 с не подтверждена. Больше измерений подряд без диагностики не запускали. Алгоритм не изменялся. Следующий вопрос — где находится время: запуск/синхронизация/выделение памяти/ядра или другой участок; без профиля это гипотезы.

## Ограниченный host CPU-профиль после timeout

Выполнено отдельно от измерений:

```bash
bash /mnt/d/semen_task_avtomat/scripts/profile-gpu-host.sh
```

perf record cpu-clock:u, 99 Hz, DWARF stack 4096 байт; дочерний процесс ограничен GNU timeout 60s. Статус 124 ожидаем для этой диагностической пробы, stdout пустой: полного CFPQ-ответа за этот интервал нет. Записано 5070 samples, 21.048 MB perf.data; Lost Samples=0. Бинарный perf.data остаётся локально в build/gpu-host-profile, текстовые отчёты находятся рядом с протоколом. Ошибки размотки/атрибуции возможны и при Lost Samples=0.

Крупнейшая собственная доля 42.90% находится в libcuda.so.1.1 по адресу 0x54a1d2 без имени функции. В стеках видны cudaStreamSynchronize и Thrust exclusive_scan/parallel_for через nsparse SpGEMM. Проценты относятся к sampled user CPU time в первых 60 секундах, не к полному wall time и не к CUDA kernel time. Включающие проценты родителей перекрываются, их нельзя суммировать. Этот профиль не доказывает причину timeout, бесконечный цикл или конкретный дефект ядра.

Проверяемая следующая гипотеза: существенны host-side накладные расходы CUDA и частые синхронизации вокруг малых матричных операций. Для проверки нужен Nsight Systems CUDA trace с числом/длительностями API-вызовов и ядер на проверенном малом входе, затем ограниченное окно luindex. Альтернатива — долгие GPU-ядра — по CPU-сэмплам не исключена. Прежде чем менять код, сопоставить обе части временной шкалы.

Итог обработки perf: self/children/DSO reports сформированы, скрипт exit0, stderr обработки пуст. Собственная доля libcuda.so.1.1 по DSO — 90.73% sampled user CPU time, cuBool — 3.27%, CFRA — 0.32%. Это усиливает приоритет исследования host/driver взаимодействия, но не означает «90.73% wall time потеряно в драйвере»: GPU, kernel-mode и неактивные ожидания этой выборкой не измеряются. Локальный perf.data сохранён, бинарные артефакты в Git не включаются.
