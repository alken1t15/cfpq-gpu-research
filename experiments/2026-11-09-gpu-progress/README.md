# Журнал продвижения GPU incremental/luindex

Дата:2026-11-09. База622f008,веткаresearch/gpu-progress-log. Статус: выполнено.

## Вопрос и изоляция

После таймаутов baseline300с нужно отличить продолжающийся расчёт от отсутствия продвижения. Сгенерирована отдельная копия incremental_algo.cpp: журнал после инициализации, на границах итераций и до/после каждого250-го вызова MxM/EWiseAdd/EWiseMulInverted. Счётчик включает только эти три типа операций, не все cuBool API. iteration_end delta — сумма новых nvals по нетерминалам, а не число новых стартовых пар. Значения берутся из уже существующего dm_total; дополнительных GPU-чтений для журнала нет.

Не меняются условия циклов/порядок операций/матрицы/маски. Для журнала добавлены счётчик, чтение host-часов и stderr с flush. Это может изменить время и планирование, поэтому диагностические времена нельзя сравнивать с baseline как speedup. Нет полного begin/end журнала каждой операции: редкий шаг250 предназначен для ограниченного объёма вывода. Остановка между точками сама по себе не указывает на конкретную функцию.

Собран только новый host object incremental.o, остальные объекты прежние; связана baseline cuBool с исправленной rowmask, без metadata trial. Production и baseline не менялись. SHA256 и точные compile/link команды в manifest.json, переносимое инструментирование — instrumentation.patch. Оригиналы дополнительно сверяются после выполнения.

## Следующий вопрос

Заметный хвост поздних итераций и большое число API-вызовов мотивируют отдельные счётчики по типам операций, размерам входных дельт и пустым результатам MxM. Нельзя объявлять поздние вычисления ненужными без математического обоснования. Следующий эксперимент должен сопоставить такой журнал на медленном/timeout запуске и успешном, различая увеличение объёма работы и замедление тех же операций. Для скоростных сравнений использовать отдельный бинарник без журнала. Production не изменён, metadata/alias/tile/streamreuse не добавлены.
