# План измерений производительности GPU CFPQ

Вопрос исследования — на каких графах и грамматиках конкретное изменение ускоряет CUDA-реализацию CFRA и чем объясняется разница. Основной режим — `incremental`. Сравнение с `base` и `lazy` — отдельный вопрос о выборе реализации. Для проверки оптимизации сравниваем исходную CUDA-сборку и сборку с одним изменением при одинаковых входах и режиме.

## Что собираем

| Уровень | Поля | Для чего |
|---|---|---|
| Серия | Дата, SHA кода, SHA-256 исполняемого файла и cuBool, флаги сборки, режим и бэкенд, команда, таймаут | Воспроизвести эксперимент и подтвердить, какая версия работала |
| Среда | CPU, RAM, модель GPU и объём VRAM, драйвер, CUDA, компилятор, ОС и WSL, питание и режим производительности | Описать условия сравнения |
| Вход | Версия FLPQ_Data, категория, граф, грамматика, SHA-256 подготовленных входов, число вершин, рёбер и меток, число правил после раскрытия шаблонов | Сопоставить одинаковые задачи и объяснить разницу между графами |
| Повтор | Конфигурация и номер повтора, признак прогрева, фактический порядок, полное время процесса, `AnalysisTime`, ожидаемое и фактическое число пар, статус, код выхода, путь к stdout/stderr | Сохранить исходные наблюдения и причины сбоев |
| Отдельное профилирование | Пиковая VRAM при одинаковом способе измерения, число итераций, вызовы MxM и других ключевых операций, времена CUDA-ядер, копирования и синхронизации | Проверить гипотезу о причине ускорения; записать инструмент, область измерения и накладные расходы |

Полное время процесса включает чтение графа, разбор грамматики, инициализацию и завершение CFRA. Конвертация архива происходит до запуска процесса. Время `AnalysisTime` берётся из внутреннего таймера CFRA. Например, в текущем `incremental` таймер останавливается перед чтением итоговых счётчиков. Чистое время работы GPU берём из отдельной трассировки. Для сравнения времени используем одинаковые границы таймеров в обеих сборках.

## Порядок запуска

1. Перепроверить корректность с исправленным импортом. Сохранить все статусы, включая расхождение с эталоном, отсутствие эталона, таймаут и ошибку выполнения. Отдельно отмечать OOM, когда это прямо видно в диагностике. Совпадение числа пар проверяет количество; для небольшого контрольного набора можно дополнительно сверить сами пары.
2. Выбрать и зафиксировать до замеров несколько закончившихся с эталонным ответом запросов разных размеров и категорий. Кандидаты — `atom` как малый контроль, `apache` как более тяжёлый C alias и `luindex` как Java points-to. Добавить подтверждённый `xz_field_sensitive_alias` для индексированных меток. В итоговую выборку включить те случаи, которые прошли проверку на обеих сравниваемых сборках; исключённые случаи и причины оставить в сводке. Список кандидатов уточнить после проверки полного каталога.
3. Для каждой конфигурации сделать один отдельный прогрев и пять измеряемых повторов. Сохранить прогрев с соответствующей пометкой. На одном GPU запускать измерения последовательно, чередуя исходную и изменённую сборки и меняя первую сборку между блоками. Применять одинаковый таймаут на один запуск, зафиксированный до начала серии. Первый протокол проверки использовал 900 секунд.
4. Проверить ответ каждого повтора. Представить по каждой конфигурации число успешных повторов, медиану, минимум и максимум. Для сопоставимости с примером отчёта также привести среднее и выборочное стандартное отклонение. Если показываем 95% доверительный интервал для среднего, указать метод и число наблюдений. Для малого числа повторов сохранить индивидуальные точки на графике.
5. Показать отношение медиан исходной и изменённой сборок по запросам, где обе серии прошли. Отдельно показать покрытие тестов и причины исключения. Время таймаута хранить как длительность до остановки. Гипотезы о причине ускорения проверять отдельным профилем на одинаковом запросе.

## Что уже есть

`results.jsonl`, `timings.csv` и сырые журналы содержат граф, грамматику, режим, статус, числа пар, полное время и, при наличии, `AnalysisTime`. Из stdout извлекаются размеры графа. `comparisons.csv` связывает успешные запуски на одинаковых задачах. Полный прогон из 465 запусков сделан со старым импортом, по одному запуску для каждой конфигурации. После исправления импорта подтверждены шесть выборочных запусков. Эти журналы подходят для диагностики и отбора кандидатов.

Перед замерами потребуется добавить повтор, признак прогрева, идентификатор сборки, хеши подготовленных входов и снимок среды. Профилирование и проверку памяти сохранить отдельными файлами для выбранных запросов.

Методика примера задаёт полезные ориентиры: описание среды, явные статусы сбоев, пять повторов и разброс. [Пример отчёта](https://github.com/RodionovMaxim05/cfl-idr-with-gll#cfl-idr-with-gll)
