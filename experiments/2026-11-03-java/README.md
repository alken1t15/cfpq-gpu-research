# Проверка индексированных шаблонов на Java luindex

Дата: 2026-11-03. Цель: проверить исправление парсера на реальном входе с опубликованным эталоном.

## Источники и среда

Граф luindex (DaCapo), данные FLPQ_Data v6.0.0. 18 532 вершины, 17 375 хранимых рёбер, 34 750 после добавления обратных. Источник графа указан архивом: https://dacapobench.sourceforge.net. Данные: https://cfpq-data.storage.yandexcloud.net/6.0.0/graph/luindex.tar.gz. Датасет распространяется как CC-BY 4.0 согласно README архива.

Эталон java_points_to.cnf: 9677 пар из reachable_pairs.csv и совпадающее количество в results.mtx архива. Оба источника относятся к одному датасету. Грамматика взята из архива без изменения.

Основа CFRA `3bc9794a509ca2f40c82b04e6c31e21ef9d1dbf1`, cuBool `1d4e760bc0d76906b81c70c505d6b29b4d9d3f11`; CPU Release GCC13.4, Ubuntu22.04 WSL2. Исходная и исправленная версии используют одну и ту же библиотеку cuBool. GPU не запускался.

## Два формата меток

`raw`: для сохранённых меток load_3, store_3 добавляются обратные load_3_r, store_3_r. Это промежуточный вход без адаптации к формату CFRA. Он намеренно проверяется как случай несовместимости форматов и не используется как корректный baseline.

`adapted`: согласованное взаимно однозначное переименование:

- load_3 → load_i_3; обратное ребро → load_r_i_3;
- store_3 → store_i_3; обратное ребро → store_r_i_3;
- alloc, assign и их обратные сохраняются.

Это соответствует шаблонам load_i/store_r_i в неизменённой грамматике и формату CFRA README. Структура графа не меняется, рёбра не отфильтровываются. Проверено, что все ID от 0 до 18531 представлены и размерности матриц совпадают. Таблица переименования и SHA256 — manifest.json.

## Воспроизведение и сравнение версий

```powershell
wsl -d Ubuntu -- python3 /mnt/d/semen_task_avtomat/scripts/check-java-cpu.py
```

Скрипт получает исходный grammar.cpp через git show записанного SHA, компилирует отдельный бинарник cfra-upstream с остальными неизменёнными production-исходниками и уже собранной неизменённой cuBool. Все остальные production-файлы дополнительно сверены с исходным SHA. Полная команда компиляции — compile-command.json. Текущая исправленная версия берётся из build-cpu-gcc13/cfra. SHA256 обоих бинарников сохранены; бинарник upstream исключён из Git.

Для каждого формата — три алгоритма × две версии, таймаут 120 секунд. Каждый запуск отдельным процессом, один повтор, без прогрева. wall_seconds в results.json — время процесса; AnalysisTime — внутренний таймер CFRA. Эти числа не используются для заявлений об ускорении: исходная версия вычисляет неправильный ответ.

## Результаты

Полные stdout/stderr и результаты каждого запуска: [results.json](results.json). Все 12 запусков завершились штатно, экспериментальный скрипт завершился кодом 0.

На raw-входе обе версии раскрывают только 5 complex-правил: индексы не обнаружены. На adapted-входе исходный парсер раскрывает 4475 правил, но использует неверные имена; исправленный раскрывает те же 4475 правил с правильными именами и возвращает эталон. Сообщения Expanded grammar сохранены в stdout.

## Ограничения

Сравниваются количества, не множества пар CFRA. Проверена одна реальная индексированная грамматика. Исправление имени в парсере не обеспечивает автоматическую поддержку исходных меток FLPQ_Data без адаптера. Нужен явный импорт/контракт формата, чтобы не получать правдоподобные неполные ответы молча.


## Вывод и следующий шаг

На реальных данных подтверждён эффект исправления корректности: при правильном импорте меток число пар меняется с 7472 на эталонные 9677. Исходная версия пропускала 2205 пар по количеству (это не доказательство включения множеств). Исправление локальное, матричные алгоритмы не менялись. Следующий шаг — формализовать импорт данных и явную диагностику нераскрытых шаблонов, затем снимать CPU baseline только корректной версии с прогревом и повторами.
