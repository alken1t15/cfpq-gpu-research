# Направления оптимизации GPU CFPQ

Рабочая карта исследований для CFRA. Все варианты ниже проверяются отдельно на одной и той же CUDA-библиотеке и одинаковых графах и грамматиках. Результаты статей используются для выбора гипотез.

## От чего отталкиваемся

- На luindex обычный incremental выполнил 96 039 MxM за 42 итерации. Из них 95 812 относятся к индексированным правилам.
- Группировка одного семейства store уменьшила число вызовов до 79 639. В отдельном замере по 1 120 пакетам упаковка заняла 5,13 с, умножение с чтением размера 1,78 с, разбор 5,59 с.
- Блочный вариант с однопроходным разбором был быстрее обычного в трёх из пяти пар, медианы 113,66 и 95,59 с. Этот эксперимент измерял общий эффект блочного варианта. Для сравнения двух разборов запущена отдельная серия.
- В профиле после раннего выхода было 613 604 передачи по четыре байта с GPU на CPU и 893 234 вызова cudaMalloc. Позднейшие правки count/fill меняют эту базу. Перед экспериментами с памятью нужен свежий профиль.

## Очередь экспериментов

| Приоритет | Идея | Что проверить сначала |
|---|---|---|
| 1 | Переиспользовать упаковку store_i в фазе Δ×M | Посчитать одинаковые упорядоченные пакеты. Убедиться по раскрытой грамматике, что правые операнды неизменны. Оценить, сколько памяти займёт кеш. |
| 2 | Подобрать размер пакета | Сравнить 4, 8, 16 и 32 отдельным опытом. Записать количество MxM, время упаковки и разбора и пик VRAM. Проверить, повторяется ли результат на другом графе. |
| 3 | Переиспользовать временную память | Выбрать по свежему профилю один часто выделяемый буфер с ясным временем жизни. Сравнить число выделений и полное время. Пул CUDA рассматривать отдельно после проверки зависимостей между потоками. |
| 4 | Уменьшить работу на рекурсивных правилах | Собрать число операций, прирост пар и объём промежуточных матриц для PTh → assign PTh и FTh → FTh assign_r. По этим данным решить, нужен ли отдельный прототип распространения. |
| 5 | Использовать CUDA Graphs для стабильного участка | Найти повторяемую последовательность с заранее выделенными буферами и определёнными зависимостями. Текущий count/fill содержит чтения на хосте и синхронизации, поэтому начинать с захвата всей итерации преждевременно. |

### Как принять решение по первому кандидату

1. Дождаться завершения сравнения разборов в data/flpq-all/store-unpack-direct. Зафиксировать исходные повторы, медианы и результат на каждом запуске.
2. Диагностическим прогоном посчитать число многоблочных пакетов Δ×M, число уникальных наборов и суммарное время упаковки повторов. Время инструментированного запуска хранить отдельно.
3. При заметной доле повторов сделать ограниченный кеш с ключом из упорядоченных символов, а для изменяемых операндов потребуется проверка версии. Отдельно учесть стоимость первой упаковки, сохранённую память и попадания.
4. Сверить точные пары на малых тестах, включая перестановку состава, смену операнда и пустые блоки. На luindex выполнить прогревы и пять чередующихся пар с одинаковым способом разбора. Контрольное число пар 9 677. Отдельно отмечать рост памяти, неуспешные запуски и разброс.

## Что дали источники

- Азимов и Григорьев формулируют CFPQ как замыкание по правилам грамматики. Это исходная модель для сверки точных пар. [Context-Free Path Querying by Matrix Multiplication](https://arxiv.org/abs/1707.01007).
- Муравьёв хранит индексированные семейства в горизонтальной и вертикальной блочных матрицах. Для CFRA ближайший опыт — сохранить уже собранные блоки с неизменными операндами. [Оптимизация 4, §3](https://arxiv.org/html/2401.11029v1#S3) · [FastMatrixCFPQ, SOAP 2025](https://pldi25.sigplan.org/details/SOAP-2025-papers/6/Universal-High-Performance-CFL-Reachability-via-Matrix-Multiplication).
- Nagasaka и соавторы группируют мелкие разреженно-плотные умножения. Их результаты мотивируют проверку размеров пакетов, а измерения относятся к SpMM. [Batched SpMM, §IV-C](https://arxiv.org/html/1903.11409#S4.SS3).
- spECK выбирает стратегию SpGEMM по предварительному анализу нагрузки. В нашем случае стоит проверить, помогает ли простая оценка числа ненулевых элементов решить, когда группировать произведения. OpSparse отдельно разбирает стоимость метаданных и выделения памяти. [spECK, §3.3](https://www.markussteinberger.net/papers/spECK.pdf) · [OpSparse, §4–5](https://arxiv.org/html/2206.07244#S4).
- POCR сокращает повторные транзитивные выводы через деревья достижимости, PEARL распространяет множества пар по графу. Skewed Tabulation сокращает промежуточные отношения с помощью преобразования грамматики и условий на порядок вывода. Для CFRA это отдельное направление с проверкой эквивалентности, включая epsilon, циклы и ориентацию рёбер. [POCR](https://yuleisui.github.io/publications/oopsla22.pdf) · [PEARL](https://enochii.github.io/publications/ase23-pearl.pdf) · [Skewed Tabulation](https://faculty.cc.gatech.edu/~qrzhang/papers/PLDI24_camille.pdf).
- Пул памяти CUDA управляет выделением и освобождением в порядке операций потока. CUDA Graphs требуют совместимого с захватом участка. cuSPARSE SpGEMMreuse предназначен для повторов с той же структурой разреженности и хранит промежуточные произведения. Для меняющихся булевых матриц приращений CFRA прямое применение этой функции пока не обосновано. [Аллокатор CUDA](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-programming-guide/04-special-topics/stream-ordered-memory-allocation.html) · [CUDA Graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html) · [cuSPARSE 12.4](https://docs.nvidia.com/cuda/archive/12.4.1/cusparse/index.html#cusparsespgemmreuse).
